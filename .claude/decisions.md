# decisions — architectural decision record (ADR)

D-001: `Board` rule code is engine-free plain C# — the puzzle is the product, so it must be unit-testable and undo must be provably exact; a `MonoBehaviour` board would make both cost a scene — affects: Board, Assets/Scripts/Gameplay/ — 2026-08-17
D-002: One seeded RNG per level attempt, seed stored with the attempt and every draw recorded in the move history — Shuffle and Mystery reveal inject randomness into a live board, and undo cannot revert what it cannot reproduce — affects: Board, Boosters — 2026-08-17
D-003: Level data stores logical colour ids; a single `BlockSkinSet` asset owns `colourId → (colour, symbol mesh)` — the whole point of this build is the reference's levels with a re-skinned symbol set, so re-skinning must be one data edit — affects: Content, Data/Levels/, Data/Blocks/ — 2026-08-17
D-004: One `Block` prefab, colour and symbol mesh applied at spawn from the skin set — 12 symbols × up to 12 colours as prefab variants is 144 assets that all have to be re-authored on a re-skin — affects: BoardView, Prefabs/BoardView/ — 2026-08-17
D-005: Bricks are 3D meshes under an orthographic camera, layered against 2D world-space slot sprites by Z position and the art pack's sorting order — the supplied art is a 2D slot pack plus 3D brick FBXs, and depth-testing transparent sprites against opaque meshes gets the front rim / back wall layering for free without a second camera — affects: BoardView, Assets/Scenes/Game — 2026-08-17
D-006: Production art sources (ImageGen raws, python processors, legacy SVG, drafts, pack docs) live in `<root>/ArtSource/`, outside `Assets/` — Unity was importing ~200 non-game files including `.py` and `.pyc`; they belong in version control but not in the asset database — affects: Assets/Art/, ArtSource/ — 2026-08-17
D-007: Columns are built with `SpriteRenderer / Draw Mode: Tiled` in exact 512 px steps rather than the fixed 2-cell `Simple` sprite — the reference's Level 79 has 4-cell columns and capacity is per-level data, so a fixed-height sprite cannot express the content — affects: BoardView, Prefabs/BoardView/ — 2026-08-17
D-008: An in-progress board is not saved; quitting a level restarts it — assumption, not an observed reference behaviour; revisit if the reference turns out to restore a board mid-level — affects: Core, Meta — 2026-08-17
D-009: Ice and Covered columns both subscribe to one `Board` event, "a colour was completed" — user-confirmed behaviour: ice thaws per completion (`thawAfterCompletions`), a cover opens when its key colour is completed (`coverKeyColourId`); one event with two readers beats two bespoke trigger paths — affects: Board, Content, Data/Levels/ — 2026-08-17
D-010: Levels are authored in a custom Unity `EditorWindow`, not hand-edited YAML and not imported from a text dump — user's chosen transcription route; it is also the only place solvability can be validated before a level ships — affects: Editor, Assets/Editor/, Data/Levels/ — 2026-08-17
D-011: A Mystery `?` cell reveals the colour the level authored for it; the reveal consumes no random value — D-010 requires solvability to be validated before a level ships and the set is transcribed 1:1, neither of which is possible if a board's hidden contents differ per attempt; this narrows the Mystery half of D-002, which still holds for Shuffle, and the RNG cursor is still recorded with every move so flipping the decision costs one method — affects: Board, Content, Data/Levels/ — 2026-08-17 (awaiting user confirmation, `OPEN-5`)
D-012: A hidden cell blocks the completion of its colour and blocks the win — without it a colour could finish while the player is still looking at a `?`, so ice would thaw for no visible reason and the win popup could appear over an unrevealed brick — affects: Board, BoardView — 2026-08-17
D-014: Every attempt scrambles its level from the attempt seed — the colour ids the level uses are permuted among themselves and the columns change slots, as one draw at level open — user-confirmed behaviour: replaying a solved level must not replay the memorised taps, and swapping the cat with the moon does not change the puzzle; both permutations are isomorphisms of a sort puzzle, so the editor's one-time solvability verdict (D-010) holds for every seed, and the scrambled level is re-validated by the `LevelData` constructor on every attempt anyway — affects: Board, BoardView, Core — 2026-08-17
D-015: A level's look is one of a **small fixed set of variants** — a pure function of (level index, variant index), the count living in `Data/Config/` — and not a fresh permutation per attempt seed: the designer has to be able to look at every board a player can ever meet, and the user's answer is that around five is enough variety; each variant reads a draw stream private to its level, so the attempt RNG stays entirely the Shuffle booster's, and `Board` never learns the count or which variant to play — both are `Meta`'s question, since both need config — narrows D-014 — affects: Board, Meta, Core, Data/Config/ — 2026-08-17
D-016: `Core` ships its own assembly definition with `references: []` — the blueprint says `Core` depends on nothing, and an asmdef cannot see `Assembly-CSharp`, so `Core` physically cannot reach `Content`, `Meta` or `UI` while they keep seeing it; the same trick D-001 uses for `Board`, and the only way `Assets/Tests/Core/` can reference `Core` at all — affects: Core, Assets/Scripts/Core/, Assets/Tests/Core/ — 2026-08-17
D-017: An attempt's seed is `f(level ordinal, attempt ordinal)`, not the clock — a board that cannot be reproduced from a bug report cannot be debugged, and the invariant banning `UnityEngine.Random` needs exactly one legal source to point at; the attempt ordinal is the save file's per-level `plays` counter, which `Meta` also rotates the variant with (D-015), so nothing extra is stored — affects: Core, Meta, Board — 2026-08-17
D-018: The save file is written at explicit flush points (level end, pause, focus loss, quit), never per changed field — worst case the file is ~80 KB (2000 level records), so one whole-file write per level is ~0.005 % of the frame budget amortised while a write per field would be ~100× that; the in-memory save is the live state and `IsDirty` is what owes the disk — affects: Core, Meta — 2026-08-17
D-019: A save that carries no version, or a version newer than the running build, is refused, kept aside as `…corrupt-n.json` and replaced by a fresh save — the alternative is a build reading fields whose meaning it is guessing at, and silently rewriting the only evidence of what went wrong; losing a save is bad, corrupting one invisibly is worse — affects: Core, Assets/Scripts/Core/ — 2026-08-17
D-020: A logical colour's look has one authority — the `BlockSkin` asset's authored colour — and the brick's URP material is *generated* from it by `Tools > Colorful Sort > Create Block Skins`; `BlockSkinSet.Validate` refuses a material whose base colour disagrees — a material and a UI colour are two hand-editable copies of one value, which is the dual-authority trap in its most ordinary form: the brick on the board and the cover stripe beside it drifting apart with nobody noticing — affects: Content, Tooling, Data/Blocks/, Art/Materials/ — 2026-08-18
D-021: The `?` brick is one slot on `BlockSkinSet`, not a thirteenth colour row — a hidden cell keeps its real colour in `Board` and only *reads* as hidden (D-012), so every mystery cell shows the same brick; that leaves `Block_Question` out of the colour map and the usable colour symbols at 11 against `BlockColourId`'s 1..12, so a twelfth colour needs one new mesh and the validation says so instead of spawning an invisible brick — affects: Content, BoardView, Data/Blocks/ — 2026-08-18
D-022: The python unitymap fallback stands down when `.claude/unitymap.md` is newer than every scene and prefab on disk — an editor export cannot carry an mtime signature, so the fallback used to overwrite the richer map at the end of every turn and report URP package scripts as `MISSING SCRIPT`; a map that lies once per turn is worse than one that is occasionally a rebuild behind — affects: .claude/hooks/build_unitymap.py — 2026-08-18
D-023: A tuning type lives with the system that reads it, while its asset lives in `Data/Config/` — `BoardLayoutConfig` is BoardView's, and the next one will be Meta's; a shared "config" system would make every tuning number everybody's business, and the assets are inventoried by assetmap.md either way — affects: BoardView, Meta, Data/Config/ — 2026-08-18
D-024: `Content` and `BoardView` each ship an assembly definition — an asmdef cannot reference `Assembly-CSharp`, so without them the blueprint's arrows were review-only and neither system could be unit-tested at all; with them `Content → Board` and `BoardView → Board, Content` are compiler-enforced, exactly as D-001 and D-016 do for `Board` and `Core` — affects: Content, BoardView, Assets/Tests/BoardView/ — 2026-08-18
D-025: A column's on-screen size is read from its own sprite's 9-slice border, not from constants — the tiled middle band is exactly one cell, so cells-in-sprite, the stud skirt below the first cell and the crown above the last all follow from three numbers the sprite carries; a normal and an ice column then differ automatically (the ice skirt hangs icicles), and no 512, 640 or 1664 can drift away from the art — affects: BoardView, Art/Sprites/Gameplay/ — 2026-08-18
D-026: The camera's framing is computed from the board's bounds plus an authored padding, never authored per level — a 12-column board and a 4-column one need different sizes, and the reference ships levels of both shapes; the only tuning number is the padding, and the maths is tested against Level 79's 12×4 on a 1440×2560 portrait viewport — affects: BoardView, Data/Config/ — 2026-08-18
D-027: `Meta` owns the attempt seam: it turns (level, variant, attempt ordinal) into a `BoardSession` and hands it to `BoardView`, which never constructs one — the view would otherwise need the seed source and the save file to draw a board, which is progression policy inside a renderer; this adds the arrow `Meta → BoardView` to the plan — affects: Meta, BoardView, Core — 2026-08-18
D-028: The Z stand-off that layers slot art and cover against the bricks is derived from the brick's own measured depth (half a brick plus a small margin), not from a chosen constant — a brick is a cube one cell deep, so a sprite 0.15 in front of the cell centre is *inside* it and the depth test hides it; the first covered column drew its cover behind the bricks it was supposed to hide, with only the parts that stuck out visible — affects: BoardView, Tooling, Prefabs/BoardView/ — 2026-08-18
D-029: A tap is hit-tested by arithmetic — `BoardLayout.SlotAt` is the inverse of the function that places the columns — and not by colliders or a physics raycast: sixteen columns and a hundred bricks stay collider-free, a board with no physics in it keeps none, and the hit test is unit-tested next to the layout it inverts, which a collider setup could never be — affects: BoardView, Assets/Tests/BoardView/ — 2026-08-18
D-030: An ice column thaws by swapping its slot sprite for the normal one — the pack ships ice as integrated art (frost shelf and icicles are part of the sprite), so there is no ice layer to switch off; the cells move down by the difference in skirt, which is harmless because a locked ice column is empty, and every brick present is re-seated anyway rather than trusted to be absent — affects: BoardView, Tooling, Prefabs/BoardView/ — 2026-08-18
D-031: Taps are refused while bricks are in flight, and starting a motion settles the previous one — the move is committed in `Board` the instant it is legal, so a mid-flight tap would act on a board the player has not seen; refusing keeps the screen honest, and settling on interruption is what makes "interrupting a tween never desynchronises the two" true rather than hoped for — affects: BoardView — 2026-08-18
D-013: A level whose data starts with a colour already gathered in one column is refused when the board is built — it hands the player a free colour, and it makes "has this colour been completed?" ambiguous for the ice and cover triggers, which are the two mechanics that count completions — affects: Board, Content, Editor — 2026-08-17
D-032: The level editor writes level assets through `SerializedObject`/`SerializedProperty`, not through setters added to `LevelDefinition`/`ColumnDefinition` — authored content keeps exactly one writer and the types stay read-only to code, while Undo, dirty-marking and asset saving come from Unity for free; the price is that the window depends on serialized field *names*, so it resolves every path once per bound level and reports a rename as an error instead of silently saving nothing — affects: Tooling, Content, Assets/Editor/ — 2026-08-18
D-033: A level authors where each column stands — one layout-grid cell per **slot**, stored on `LevelDefinition` as `row × layoutColumns + column`, with an empty array meaning the plain fill it meant before — because a board of three columns over four cannot be expressed by a dense grid at all; the cell belongs to the slot and not to the column standing in it, which is why it does not live on `ColumnDefinition`: an attempt permutes the columns among the slots (D-014), so a position that travelled with its column would make the permutation invisible, and `Board` still never learns a position — affects: Content, BoardView, Meta, Tooling, Data/Levels/ — 2026-08-18
D-034: Each row is centred on its own occupied span, and a cell left empty inside a row keeps its width — three columns over four then read as three centred over four, which is what the reference looks like, rather than three pushed against the left edge; the cost is that a deliberately off-centre row cannot be expressed, and the whole rule is one private function (`RowSpan`) if that ever has to change — affects: BoardView, Tooling — 2026-08-18
D-035: The solvability search lives beside the rules it drives, behind `#if UNITY_EDITOR`, rather than under `Assets/Editor/` — an editor-only folder compiles into `Assembly-CSharp-Editor`, which no test assembly can reference, and an unverified validator is worse than a few kilobytes of code that never ships; the `#if` keeps it out of every build, the file uses no `UnityEngine` type so `Board` stays engine-free (D-001), and it drives a real `BoardSession` instead of re-implementing the move rule, so the verdict is about the game rather than about a second rulebook. Its depth cap is `BoardMoveHistory.MaxEntries`, not a chosen number: one move deeper and the history would drop the entry the search needs to undo — affects: Board, Tooling, Assets/Tests/Board/ — 2026-08-18
D-036: `Meta` and `UI` each ship an assembly definition, added together because the second forced the first — an asmdef assembly cannot reference `Assembly-CSharp`, where `AttemptStarter` was compiling, so a `ColorfulSort.UI` assembly could not have seen the very seam it has to send restart through; the alternative was to leave `UI` outside the asmdef scheme and give up the compiler-enforced arrows D-001, D-016 and D-024 established for every other system. Both are `autoReferenced`, so `Assembly-CSharp-Editor` and `BoardViewPrefabFactory` still compile against `Meta` — affects: Meta, UI, Assets/Scripts/Meta/, Assets/Scripts/UI/ — 2026-08-18
D-037: `BoardInput` refuses a press that lands on a UI graphic, asked as an `EventSystem` raycast at the press position — the gear sits over the board and every popup covers it, so without this the tap that opens Pause also lifts a brick behind it. It is not `rules/gameplay.md`'s banned reference to `UI`: the ban is about `ColorfulSort.UI`, and nothing in `BoardView` names a type from it, while `EventSystem` is the engine's input router in the same category as `Camera` — a judgment call, so it is recorded rather than made quietly, and its cost is `UnityEngine.UI` on `ColorfulSort.BoardView.asmdef`. The raycast is preferred to `IsPointerOverGameObject()`, which answers for whichever pointer the UI module processed last and is documented as needing a pointer id to be right about touch; the raycast has no pointer identity to get wrong. It makes the HUD responsible for something in return: any full-screen graphic left as a raycast target swallows every tap meant for the board — affects: BoardView, UI, Tooling — 2026-08-18
D-038: `UI` learns how an attempt ended from `Meta`, not by subscribing to `BoardSession` itself — `AttemptStarter` forwards `Won`/`Deadlocked` as `AttemptWon`/`AttemptDeadlocked`; the alternative was to widen `AttemptOpened` to carry the session so the HUD could attach to `Board` directly, which would put `ColorfulSort.Board` on `UI`'s assembly and a second system on `Board`'s events for nothing. The arrow `UI → Meta` already exists, and the seam that owns which attempt is being played is the honest owner of how it ended; the forwarding is re-hung on every new session while the listeners stay on the component, because a restart builds a new `BoardSession` and subscribing once would give a Win popup that fires exactly one time — invisible until somebody replays a level — affects: Meta, UI, BoardView — 2026-08-18
D-039: An attempt's seed is built from the level's **ordinal**, not from the number on its plaque — `fingerprint.md` and `AttemptSeedSource`'s own documentation always said `f(level ordinal, attempt ordinal)`, and the save carries exactly those two, but the code passed `LevelIndex` because until 5A there was no ordinal to pass; the cost is that inserting a level mid-database changes the *scramble* of every later level, which is harmless because every variant is a solvability-preserving isomorphism (D-014) and no board is stored — affects: Meta, Core — 2026-08-18
D-040: Progression reads and writes in two separate steps — the attempt ordinal is read to build the seed, and the play is recorded only once the board is actually on screen — because an attempt that fails to open must not consume a play; a consumed play silently changes the board the next honest attempt deals, which is a bug that reaches the player's save file and cannot be undone the way a board can. The same reasoning makes `CompleteCurrentLevel` idempotent and puts a range repair in the constructor: a save outlives the database that produced it — affects: Meta, Core, Assets/Tests/Meta/ — 2026-08-18
D-041: A shuffle records the colour every cell held **before** it ran, rather than leaving undo to rewind the RNG and recompute the permutation — this reverses the assumption in its own task's preflight, which argued that storing it would duplicate what the seed already determines. Writing it made the contradiction plain: the derived design is precisely the failure the same preflight named as its worst risk, an undo off by one draw that restores a board which looks right and is not, with nothing on screen to say so. A recorded before-state cannot be off by anything, and it costs one array of at most 128 entries at booster frequency — affects: Board, Assets/Tests/Board/ — 2026-08-18
D-042: `OPEN-3` is answered: **there is no hearts system**. The user's call — a deadlock shows the Fail popup and costs nothing, no life is spent anywhere, and there is no refill timer or out-of-lives screen. `hearts` and `heartRefillUnixMs` stay in `SaveData` because removing a field from a written save shape would be a `saveVersion` bump for nothing, but no code reads or writes them; if lives are ever wanted, that is a feature with its own task and the fields are already there. This removes hearts, the refill and the lives gate from task 5B, which is now coins and boosters only — affects: Meta, Core, UI, scope.md, fingerprint.md — 2026-08-18
D-043: Boosters are free — no coins, no charges, no cost. The user's decision, taken after `OPEN-3` had already removed lives (D-042), and it cancels the planned economy task outright: `coins` joins `hearts` as a `SaveData` field nothing reads. What it buys is that the three boosters are reachable and testable now instead of behind a currency nobody has designed a source for — ads and IAP are out of scope (fingerprint.md → Network model), so a coin would have had to come from clearing levels, which is a balance question this project has no content to answer yet. Adding a price later changes `Meta` and leaves every button and every board rule alone — affects: Meta, UI, Core, scope.md — 2026-08-18
D-044: A booster's result is drawn by rebuilding the board from `Board`'s state, not by animating the change — `BoardView.Resync`. An undo can restore a cover, a lock and a hidden cell in one step and a shuffle rewrites every visible cell, so three bespoke reverse-tweens would be three more ways for the screen to contradict the board, which is the failure D-031 exists to prevent and the one that stays invisible: a plausible wrong board only misbehaves on the *next* tap. The tap path keeps its lift-arc-drop; only boosters snap — affects: BoardView, Meta — 2026-08-18
D-045: Music is its own persisted setting, and a round toggle draws its state as a **pair of icons** instead of one icon under a diagonal bar. The user re-skinned the Pause row with the second UI set, which ships every toggle icon as an on/off pair and ships no slash at all — so "off" stopped being a composite of two graphics that had to line up, and `SettingToggleButton` now flips `onIcon`/`offIcon`. Two consequences were not optional: the `Setting` enum is numbered explicitly and only appended to, because those ints are serialized in every popup prefab and an inserted value would silently turn the Vibration button into a Music button; and `musicOn` in `SaveData` is a save *shape* change, so `CurrentVersion` goes 1 -> 2 with a step that sets it on — a bool that `JsonUtility` defaults to `false` cannot say whether a player chose silence or never had the field, and only the version can tell those apart. Restart left the row in the same pass, having been the one round button whose off-state graphic was built and thrown away: a command has no on/off state — affects: UI, Core, Tooling, Assets/Tests/Core/ — 2026-08-19
D-046: The board is framed against the band the HUD leaves it, not against the screen, and every column placement is **derived** from the level's authored one rather than edited in place. Both came out of the first playable render: the board slid under the plaque and the booster bar, and undoing an added column left its cell — and the row it had started — reserved. `BoardLayoutConfig` gains `topReserve`/`bottomReserve` as shares of viewport height, measured from the scene (plaque 255 px and booster bar 300 px of the canvas's 1920) but **stated** rather than read: gameplay holds no reference to UI (rules/gameplay.md), so reading a Canvas rect from the view would reverse the blueprint's one-way arrow and produce a number no unit test could pin. The cost is that a HUD which grows needs the asset edited to match, and that a device with a deep notch gets a slightly generous top gap rather than a short one. `BoardLayout.PlaceColumns` replaces the grow-only `EnsurePlacementFor`: keeping the authored array untouched is what makes an added column distinguishable from an authored one after the fact, and it moves the rule out of a MonoBehaviour into the pure layout maths where the defect is testable — affects: BoardView, Assets/Tests/BoardView/, Assets/Data/Config/ — 2026-08-19
D-047: Bricks are turned to face the camera in the `Block` prefab (Y 180°), not re-exported. Measured from the FBX geometry rather than eyeballed: the embossed symbol sits on the mesh's +Z face — `Block_Cat` carries 845 vertices at max-Z against 124 at min-Z, `Block_Star` 284/124, `Block_Question` 968/124, and the min-Z count is identical across all three because that is the plain rounded back. The camera sits at z −10 looking along +Z, so every brick showed its back. One prefab value fixes twelve meshes, survives pooling (`BlockPool.Return` resets position only) and stays true if a mesh is re-exported; the alternative, a rotation baked into twelve FBX importers, is twelve places to get wrong — affects: BoardView — 2026-08-19
D-048: A column sprite's nine-slice border means exactly one thing: **bottom = skirt, top = crown, the band between them = cells**. The pack's art folded one cell into its bottom border and `ColumnMetrics.FromSprite` subtracted it back out, which made the same field mean two things — and the user's hand-drawn tray, whose skirt is a 3D base plate rather than a drawn cell, cannot be read that way at all. Rather than carry a second rule, the pack's borders are re-stated to say the same skirts they already produced (normal 832 -> 320, ice 1152 -> 640) and the rule loses its subtraction. The draw mode follows from the same reading: a band measuring a whole number of cells has per-cell detail and tiles (D-007, capacity you can count), anything else stretches, so `TilesPerCell` is the sprite's answer instead of a prefab setting somebody has to keep in step. The hand-drawn art also brings its own pixels-per-unit (160, measured from its 188 px interior), because a painted rail's edge is not on a slice boundary and only a measurement can say how wide the drawn interior is — affects: BoardView, Tooling, Assets/Tests/BoardView/ — 2026-08-19
D-049: A brick's facing belongs to the `Block` prefab, and `ColumnView.Place` no longer writes rotation. It forced `Quaternion.identity` on every seat, which silently overrode the prefab every time a brick was placed — so D-047's 180° turn changed the asset and nothing on screen, and the symbols went on facing away. Nothing in the view rotates bricks, so there was nothing for the reset to undo; what it actually did was give two places an opinion about the same transform, with the runtime one winning invisibly — affects: BoardView — 2026-08-19
D-050: The Game camera leans 25° into an upright board, and the **scene owns that angle**. `BoardLayoutConfig` deliberately does not gain a tilt field: the camera's rotation is already the single writer of how the board is looked at, and a copy in the config would silently beat the Inspector value the user tunes. The framing *reads* the angle instead — an upright board projects onto the screen's vertical axis by its cosine, so a tilted camera zooms in rather than out, and width is untouched — and the position is rebuilt from the camera's own `up` and `forward` rather than world axes, because the reserved HUD bands are measured along the camera's up and adding them to world Y would mis-centre them by that same cosine. The distance is taken along the view ray, not as a depth in z: the band's own z component would otherwise be added back on every resync and the camera would creep away from the board a fraction per booster press. The tap becomes a ray against the board's plane, because `ScreenToWorldPoint` returns a near-plane point whose x and y only match the board while the camera looks down its normal — tilted, taps drift a whole row, which reads as a rule bug and is not one. Backgrounds need no work at all: they are children of `--Camera--`, so they inherit the lean and stay square to it — affects: BoardView, Assets/Scenes/Game.unity, Assets/Tests/BoardView/ — 2026-08-19
D-051: A brick is seated by a **relationship to the brick that would be below it**, not by an offset to its cell. V-2 aligned the base plate's studs with the first cell's floor, which reads as correct and is not: a brick's body starts a little above its cell floor, so the studs stood in the open — the thing the plate exists to prevent. The rule is now that the plate's studs end exactly where a brick standing one cell lower would end its studs, which is two mesh measurements and no constant, so re-exporting either mesh moves the plate on its own. The same misreading at the other end: the tray's top border was set generously at 40 px, which put the cell ceiling below where the art's interior actually begins and left the wavy top floating above the highest brick's studs. 28 px — the largest interior start measured across the sprite's width — is both the smallest border that keeps the wave out of the stretched band and the ceiling that puts the studs inside the wave. Both ends of a column are now art measurements rather than chosen numbers — affects: Tooling, BoardView, Assets/Tests/BoardView/ — 2026-08-19
D-052: An engraved symbol is painted by a **second material**, and its colour is **derived** from the brick's. The re-authored meshes carry the symbol's faces in their own slot, so `BlockSkin` gains a symbol material and `BlockView` assigns both (still `sharedMaterials`, so nothing clones — D-004). The colour is `uiColour` times `BlockSkinSet.symbolShade` (0.65) rather than twelve authored symbol colours: the set is already the single authority for what a colour looks like (D-003), and twelve more hand-picked values would be twelve more chances for a brick and its own symbol to drift apart. The same reasoning gives the base plate a generated `Slot_Base.mat` whose colour is **sampled from the tray PNG** it sits in — the art stays the authority, a re-exported tray brings the plate with it, and the plate stops rendering magenta, which is what an FBX material on a shader URP does not know looks like. Two consequences worth stating: a skin with no symbol material is a content defect (`IsAssigned`), so the board refuses to draw until the generator has run once; and `BlockSkinFactory` now has to skip `Block_Base`, which shares the models folder and the `Block_` prefix but is a floor, not a colour — affects: Content, BoardView, Tooling, Assets/Data/Blocks/ — 2026-08-19
D-053: How the art sits inside a column is the **prefab's** value, not the build tool's. V-3b had the tool write the base plate's position on every run, which fixed a real misalignment and then showed its cost: the user tuned a live column by eye — tray scale (0.947, 0.9953) with a 0.009 centring nudge, plate scale 1.0972 at y 0.20196 — and the next run of the tool would have reset it to the formula's answer. Those four numbers now live in `Column.prefab`, where the two variants inherit them, and the tool is back to what its own header promises: an existing prefab is left as it is. The derived relationship (D-051) remains the value a *new* plate is created with. They are deliberately not in `Data/Config` — they describe how one piece of art sits against another, and the ice column's art has different proportions and will want its own. The 0.009 is not taste either: `slot.png`'s opaque area is 1.5 px off-centre in a 199 px sprite, which at 160 px per unit is 0.0094 — affects: BoardView, Tooling — 2026-08-19
D-054: The row gap is sized by the **lift**, not by taste: 1.2 units against 0.6.
